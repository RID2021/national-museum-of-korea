# Repository Guidelines

## Project Structure & Module Organization
`main.ts` bootstraps the ZEP app by subscribing to lifecycle hooks such as `ScriptApp.onInit`, `onStart`, and `onDestroy`. Place reusable logic in `src/` modules (e.g., `src/add.ts`) and import them into the entrypoint. Static assets and generated bundles land in `res/`, while deployment metadata and tooling live at the repo root (`zep-script.json`, `webpack.config.js`, `deploy.sh`).

Inside `res/`, use subdirectories so asset types stay separated:
- `res/html/` for widget templates or other HTML payloads referenced by widgets.
- `res/images/` (and other folders as needed) for sprites, thumbnails, or supporting art.
- `res/main.js` and other build outputs stay at the root of `res/` as generated by the toolchain.

If a required subdirectory does not exist yet, create it before adding new files. When adding functionality, prefer creating a dedicated `.ts` module under `src/` and, if UI is involved, pair it with an HTML template in `res/html/` that the script loads explicitly. Keep widget HTML or JSON payloads versioned alongside the scripts that reference them by mirroring this structure.

For developer-only overlays, use `src/utils/message.ts`. The exported `debugMessage` helper wraps `ScriptPlayer.showCustomLabel` to surface `[DEBUG]` notices to admins (`player.role > 1000`). Set `NODE_ENV=production` or `ZEP_DEBUG=false` during a build to silence the helper automatically; otherwise it defaults to on while developing locally. Avoid `console.*`—log through `debugMessage` so ZEP-compatible admins see the output without runtime errors.

Whenever you need to stash per-player state (like widget references), call `preparePlayerTag(player)` from `src/utils/player.ts` to guarantee `player.tag` exists before writing custom fields. Use `preparePlayerStorage(player, defaults)` to bootstrap a JSON payload in `player.storage`, and `savePlayerStorage(player, data, { persist: true })` when you need to immediately flush changes (mirrors the sample Q-key purchase flow).

## Build, Test, and Development Commands
Install dependencies with `npm install` before first use. `npm run build` invokes `zep-script build`, compiling TypeScript and checking for API misuse. `npm run pack` rebuilds and archives to `.zepapp.zip`, whereas `npm run archive` reuses the existing build for quick packaging. Use `npm run deploy` to run `zep-script publish`; confirm credentials and target space IDs inside `zep-script.json`.

## Coding Style & Naming Conventions
Follow TypeScript conventions with 2-space indentation, explicit return types, and trailing semicolons. Name files after the exported symbol (`ScriptApp` helpers like `onJoinPlayer.ts`), keep classes in PascalCase, and Pure functions in lowerCamelCase. When wiring events, group related listeners (e.g., `ScriptApp.onPlayerTouched`) inside descriptive modules. Document complex `ScriptMap` or `ScriptWidget` flows with brief comments that reference the corresponding API table from `zep-script-guide.md`.

## ZEP Script API Usage
Use `ScriptApp` lifecycle callbacks to orchestrate startup (`onInit`, `onStart`), player churn (`onJoinPlayer`, `onLeavePlayer`), and teardown (`onDestroy`). Manipulate world state through `ScriptMap` methods like `putObject`, `addOnTileTouched`, and timed helpers (`setTimeout`, `setInterval`). Interact with individuals via `ScriptPlayer` APIs—`showCenterLabel`, `spawnAt`, `playSound`—and communicate with UI overlays through `ScriptWidget.sendMessage`. Prefer storing persistent state with `ScriptApp.storage` and guard any restricted 🔒 fields behind null checks.

## Testing Guidelines
Treat `npm run build` as a gating step; it surfaces type errors and missing imports. For behavioral validation, stage the app in a sandbox space and exercise lifecycle hooks, especially collision callbacks like `onObjectTouched`. If you add automated tests, organize them under `src/__tests__/` and mock `ScriptApp` interfaces so timer utilities (`runLater`, `setInterval`) remain deterministic.

## Commit & Pull Request Guidelines
Write imperative, one-line commit subjects (`Add player spawn helper`) similar to existing history. Reference issues when applicable and keep each commit focused on a feature or fix. PRs should outline the scenario, list impacted API hooks, and include screenshots or GIFs when the change affects in-world visuals. Highlight any required updates to `zep-script.json` or widget assets, and note post-deploy verification steps for reviewers.

## Deployment & Configuration Tips
Mirror any script changes inside `deploy.sh` so CI can reuse the same command chain. Configure environment secrets for the ZEP CLI outside the repository, and document required variables in the PR body. After `npm run deploy`, confirm the published build by checking player counts or widget state via `ScriptApp.players`, and tag releases only after validation.
